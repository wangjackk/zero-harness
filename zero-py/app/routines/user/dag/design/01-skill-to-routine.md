# 01 · skill → routine:从解释执行到编译执行

## 问题:提示词定步骤不稳

一个 skill 用自然语言描述"该怎么做这件事"的 N 个步骤,每次运行都要 LLM **重新解读 + 重新生成执行轨迹**.不确定性沿步数链式累积(见 00 篇原则三的数学).

步骤越多,偏离概率越高.这不是模型不够聪明,是**架构把太多确定性的活儿交给了一个非确定性的执行器**.

---

## 核心视角:LLM 从"解释器"退役为"编译器"

| | 形态 | 特征 |
|---|------|------|
| **提示词 skill** | 解释执行(interpreted) | 每次运行都让 LLM 现场"解释"步骤;慢,贵,每次结果可能不同 |
| **routine / 固定步骤** | 编译产物(compiled) | 步骤被一次性固化成确定的可执行物;快,确定,可复现 |

`skill → routine`,本质就是 **解释执行 → 编译执行** 的迁移.

LLM 的角色随之转变:它不再是"运行时的解释器",而是**编译期的代码生成器**----把一个模糊意图编译成一段确定流程,**编译一次,确定复用多次**.

### 这条线 Zero 里已经画完了:`save.py`

`save.py` 让 LLM 把探索出的有效 routine 组合**存成命名 routine** 落盘到 `routines/user/_xml/*.xml`,下次启动 `load_xml_dir()` 自动编译成 `BaseRoutine` 子类.

- `skill` = 探索期的解释脚本
- `routine`(save 产物)= 固化后的编译产物
- `save` 这个动作 = LLM 自动编译

`bash`/`script` 这类固定节点是**人类手工编译**的结果;`save` 是 **LLM 自动编译**的结果----更进一步.

---

## 生命周期:skill 不是 routine 的劣化版,是它的前身

```
提示词 skill(探索期:灵活,能适应未知)
      │  稳定下来,值得复现时
      ▼
固化成 routine / DAG 节点(生产期:确定,可复现)
```

skill 和 routine 是**同一个能力在不同成熟度的两种形态**,不是二选一.

**实践推论**:一个真实流程里各步骤的成熟度是不均匀的----有的已稳定到该编译,有的还嫩到必须靠智能临场扛.所以最终形态不是"全 routine"也不是"全 skill",而是**一张能让两者按成熟度共存的图**(这正是 RunDag 要支持固定节点 + AI 节点混排的理由,见 02,03 篇).

---

## "现阶段"这个限定词:边界会移动,但不会消失

这条"确定性边界"放在哪,取决于模型可靠性:

- 模型越弱 → 边界越往"全固化"推(只敢让 LLM 做最小判断)
- 模型越强 → 边界越往"提示词"那侧退(敢把更多步骤交回 LLM 临场)

**但即使模型强到永不出错,固化仍然有价值**----理由会从"因为 LLM 不可靠"**变成**"因为我需要可复现,低延迟,低成本,可审查".

固化是**用能力换可控**,这个需求独立于模型强弱存在.所以这个理念不会过时,只会**重新划线**.

---

## 给实现的指引

- `save` / 固化机制应保留**输入契约**(这个 routine 吃什么参数)和**输出契约**(产出什么),见 04 篇的子工作流契约----固化产物和子工作流本质同构:都是"吃 kwargs,吐 result 的黑盒 routine".
- 不要过早固化还在演化的流程,否则丢掉 LLM 的适应性.判断标准一句话:**下一步该做什么是已知的 → 固化;要靠 LLM 当场想 → 留提示词.**
