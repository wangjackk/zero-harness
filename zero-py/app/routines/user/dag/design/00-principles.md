# 00 · 三条地基原则

这三条是后面所有设计的根.任何新功能落地前,先用它们对一遍.

---

## 原则一:万物皆 Routine(含编排器,含 LLM)

一个 routine 只有三件事:

```python
class BaseRoutine:
    def modules(self): ...      # 用什么资源
    async def start(self): ...  # 怎么做
    async def stop(self): ...   # 怎么停
```

TTS 是 routine,搜索是 routine,机械臂是 routine----**连 LLM 推理(Think)本身也只是一个 routine**.它不凌驾于系统之上,和说话,走路一样被调度,被中断,被组合.

**推论**:编排器(决定一组任务怎么跑的东西)也必须是一个 routine,不是一个独立的特殊组件.这条推论是 03,04 两篇的地基.

---

## 原则二:机制 vs 策略分离(操作系统级的关注点分离)

| 层 | 职责 | 归属 |
|----|------|------|
| **机制(mechanism)** | 一个被 push 的 routine 怎么跑:资源互斥,同层并行,树形中断,生命周期 | **Shell(Go 内核)** |
| **策略(policy)** | 什么时候 push 哪个 routine | **应用层 routine** |

**Shell 不该知道也不需要知道"为什么这个 routine 在这个时机被 push".**

push 时机的决策权可以来自不同的"大脑",它们全是平级的应用层 routine:

| 谁来决定下一步 push 谁 | 实现 |
|---|---|
| LLM 临场决定 | Think / Act routine |
| 静态图决定 | RunDag routine |
| 时间决定 | Alarm routine |
| 外部事件决定 | Trigger |
| 人类决定 | Approval gate routine |

### 为什么策略绝不能进 Shell

1. **SRP**:Shell 的契约干净到极致(push 进来 → 管好生命周期).塞进 `depends_on` / `when` / 并行层 / resume,调度内核就被业务语义污染了,而业务语义会随产品不断变.
2. **策略是开放集合,机制是封闭集合**:DAG 进了,ReAct 循环要不要进?定时要不要进?把所有时机策略留在应用层,Shell 保持中立,无穷多种编排模式才能平等共存,自由组合(甚至混合:DAG 里嵌一个 LLM 决策节点).
3. **蝉蜕需要稳定内核**:Shell 是支撑自我迭代的底座,是整个体系里最不该频繁变动的部分.机制要稳,策略要活.

> **Shell 提供"push 这个动作"和"调度被 push 者";谁来 push,何时 push,按什么逻辑 push----是上层 routine 的自由.**

## 原则三:确定性边界(把不确定性压到最小)

把工作尽可能多地从"LLM 解读提示词"挪到"确定性执行",只把**不可外包的不确定性**留给 LLM.

**数学根源----误差随步数放大**:一个 N 步流程,每步靠 LLM 现场解读+生成,每步哪怕 95% 可靠,5 步连起来就是 `0.95⁵ ≈ 77%`,10 步掉到 60%.把其中 8 步钉成 100% 确定的代码,只在真正需要判断的 2 步用 LLM,整体回到 `0.95² ≈ 90%`.

**你不是让 LLM 变强了,你是把它的职责面压缩到了最小.** 详见 [01-skill-to-routine.md](./01-skill-to-routine.md).

边界会随模型可靠性移动,但**不会消失**----见 01 篇结尾.
